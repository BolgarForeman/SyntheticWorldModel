WORK ORDER 1 — Spawn tree, recipe schema v1, the pilot recipe, first identity check

Precondition: pull request #1 (the scaffold) is merged. Start from an up-to-date main on branch wo1/recipe-and-streams.

Goal: a recipe goes in and comes out resolved, versioned and hashed, and every random stream the generator will ever use is fixed by name off the root seed. The same recipe and seed must give the same bytes on Windows and Linux. Nothing is generated yet; this is the contract every later stage reads from.

Spec: World_Generator_Structure.md v0.2, §3 (principles) and §4 (stages, for the fields each stage reads). CLAUDE.md §4 and §7. The recipe's field list comes from Interface_Mockup_v0_5.dc.html: the state defaults in the constructor (around lines 519–541), and the `recipe` array and the definition tables in renderVals (layerDefs, drawnDefs, errDefs, baseRates, classDefs, modelDefs, objDefs, weightDefs). Read those as the field inventory, not as code to port.

Build:

1. The spawn tree (src/swm/rng.py).
   - `stable_id(name: str) -> int`: the first 8 bytes of SHA-256 of the UTF-8 name, read as a big-endian unsigned integer. Never Python's hash().
   - `stream(root_seed: int, path: str) -> numpy.random.Generator`. The path is slash-separated and hierarchical (for example "terrain", "layers/power/siting", "errors/osm_power"). The seed is `SeedSequence(root_seed, spawn_key=tuple(stable_id(part) for part in path.split("/")))`, and the generator is PCG64.
   - A registry of every stream path the generator uses, with a one-line purpose each. Populate it now for every stage in the spec, even though no stage draws yet. It is the spawn tree that gets written beside every world.
   - `stream_record(root_seed)`: for every registered path, its spawn key and the first four 64-bit integers drawn from it, as a sorted, serialisable structure. This is what the identity check compares.

2. Recipe schema v1 (src/swm/recipe/): pydantic v2 models covering the full recipe the mockup defines, in its sections:
   - header: recipe_version, root_seed;
   - terrain;
   - layers (per layer: state, node count, links per node, nodes-only, sources, overlap), plus dual membership;
   - couplings: the supplier→consumer pairs switched on; handling of switched-off pairs; density; two-way; supplier-not-nearest; concentration; feed mix;
   - shared causes: hazards and scenarios;
   - unobserved: the five drawn quantities with heterogeneity and compliance gap, plus crews and depots;
   - dynamics and difficulty;
   - errors: mechanism, plus per-source coverage, snapshot age and the seven rates;
   - ensemble;
   - answer_key_requests.

   Rules for the schema:
   - Every field has a type, units in its name where it has units (area_km2, window_h, correlation_km, snapshot_age_y), an allowed range, a default, and a docstring or Field description saying what it controls, in the spec's words.
   - Shares the interface shows as percentages are stored as percentages, named with a _pct suffix, 0–100. The feed mix must total exactly 100; validate it.
   - Enumerations are closed:
     - map types: the mockup's eleven;
     - urban patterns;
     - layer states: emitted, hidden, off;
     - layers: power, telecom, water, transport, fuel, healthcare;
     - sources per layer: the mockup's list;
     - hazards: storm corridor, seismic zone, flood plain;
     - tiers: exact, simulation, both;
     - error mechanisms, adversarial included;
     - optimization member-classes: defensive, offensive, restorative, informative;
     - objectives;
     - weight presets.
   - The default coupling set is the 21 the spec models. Healthcare supplies none. Record the list in the schema, not in a comment.
   - A source may be switched on only for its own layer. The links rate is ignored for a nodes-only layer; record that as a validation note, not an error.
   - The size presets (hand-check, small, Taiwan-scale, very large, huge) set area and node counts. The Taiwan-scale values are marked placeholder (open decision: realism ranges and Taiwan-scale counts).
   - The whole recipe is accepted now (ruling 2026-09-28). A buildability check reports every feature the recipe uses that is not yet built, and the phase it arrives in, from a single table in the code. `swm build` will refuse such a recipe with that list; for now the check is callable on its own. Adversarial error is always refused ("carried in the schema, not exercised").
   - An unknown recipe_version fails with a message naming the versions this code reads.

3. Loading, resolving, writing (src/swm/recipe/):
   - load YAML → validate → resolve, so that every default is filled in and the preset is expanded;
   - write the resolved recipe as canonical YAML: fixed key order (schema order), LF, UTF-8, no timestamps, floats written the same way on every platform;
   - compute recipe_sha256 over the canonical bytes. Later answer keys and manifests will carry it.

4. CLI: `swm resolve RECIPE -o OUT_DIR` writes resolved_recipe.yaml and stream_record.yaml. `swm check-recipe RECIPE` prints validation notes and the buildability report. Nothing else.

5. The pilot recipe: tests/fixtures/pilot_hand_check.yaml, taken from Pilot_Spec.md:
   - hand-check size, 4 nodes per layer, spine island;
   - all six layers emitted, one source each;
   - the default 21 couplings;
   - storm corridor on, with 8 scenarios;
   - exact tier;
   - parametric errors;
   - answer-key requests:
     - defensive, protect condition and add reserve, budget 3 and budget 4;
     - offensive, strike nodes, k = 2 and k = 3;
     - restorative, two crews;
     - informative, observe one coupling.
   Objective unserved demand-hours throughout, healthcare-first weights. Where the pilot spec is silent, use the schema default and list the field in your report.

6. Tests:
   - rng: stable_id is fixed (golden values for a few names); adding a path to the registry never changes any existing path's stream (property test); different paths give different streams; the same path and seed always give the same draws.
   - schema: every default validates; out-of-range values, a feed mix not totalling 100, and a source on the wrong layer are rejected with clear messages; an unknown version is rejected; round trip (load → resolve → write → load → resolve → write) is byte-identical.
   - identity (golden): the resolved pilot recipe and its stream record are checked in under tests/golden/ with their SHA-256. CI must reproduce both hashes exactly on Windows and Linux.
   - buildability: the pilot recipe reports exactly the features it uses, each mapped to Phase 1, 2 or 3; a recipe using a later-phase feature reports that feature and its phase.

Acceptance:
- All checks pass locally and in CI on both platforms.
- The golden hashes match on both platforms.
- `swm resolve tests/fixtures/pilot_hand_check.yaml -o <dir>` produces the two files, and a second run produces identical bytes.
- Coverage stays at or above 90%.

Out of scope:

Do not draw from any stream except in rng tests and stream_record.

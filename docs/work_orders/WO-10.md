# PR 10a — The frame and the restorative model

PART A — REQUESTS AND RECIPE SCHEMA VERSION 4

A1 Schema version 4, with these request fields (ruled Q3, Q4, Q6, Q2):
- `strike_nodes`: `world` (`calm`; the only value for now) and `strike_damage` (`complete`; the only value for now).
- `protect_condition_and_add_reserve`: `reserve_hours` (`window`; the only value for now: the request's window at the node's full draw).
- `sequence_repair_crews`: `scenario`, the scenario index, required.
- A version 3 recipe migrates on loading, with the defaults above. A version 3 `sequence_repair_crews` request has no scenario, so it fails with a clear message naming the field.
- `observe_uncertain_couplings` stays in the schema. `swm solve` refuses it with "the informative answer key is built in Phase 4, against the pipeline's belief".

A2 The pilot recipe (`tests/fixtures/pilot_hand_check.yaml`) carries ten requests (ruled Q12), each with a 72-hour window:
- defensive at budgets 3 and 4;
- offensive at k = 2 and 3;
- restorative on scenario 7.
Each of the five appears twice: under the Lifeline weights and under the Equal weights. Every golden's resolved recipe moves with this; explain it as such.

PART B — THE KEY

B1 `swm solve <recipe> --out <dir>` builds the world in memory and writes one key per request to `<dir>/answer_keys/`, plus an index listing them. `swm build` does not solve: keys can take a day.

B2 Requests that differ only in their service weights share one search: the runs record each end use's hours out, and each weighting is arithmetic on them (ruled Q12).

B3 Every key holds (spec v0.17 §5; ruled Q11):
- **the stamp:** "assumes:" with class, model, objective, service weights, budget, window, the scenarios (all, calm, or the named one) and the resolved recipe's SHA-256;
- **the optimum:** the answer and its objective, every tied answer listed;
- **the measure:** distance from the optimum = (objective − optimum) ÷ (no-action objective − optimum), mirrored for the offensive model. If no action already equals the optimum, the range is zero: report it, and report every distance as undefined. Do not divide;
- **the spread:** the share of all affordable answers within 1%, 5% and 10% of the optimum, and a random answer's mean distance (the mean over all answers). Every affordable answer counts, including those skipped as provably identical (E4), each with the score it is proven to have. The three bands are registry rules: 1, 5 and 10%, grade J, source ruling Q11 (Phase 2 ruling sheet v0.2);
- **every answer and its objective under each weighting,** kept beside the key in a compressed file with fixed metadata, so the spread can be audited and recomputed;
- **each rule of thumb's answer and its distance** (Part B4);
- **true criticality:** for each of the 24 nodes, the objective when that node alone takes complete damage, less the objective without it, under the request's own scenarios and weights (ruled Q11). The damage is added at hour 0 on top of each of the request's scenarios: each of the 8 storms, averaged, for the defensive model; the calm world for the offensive model; scenario 7 for the restorative model. The crews work in the default order, as for a strike (Q4);
- **the dose:** 0, with the note "no error planted until Phase 3";
- **the note:** "optimal against the scenarios named in the stamp, a sample of the storm, not the storm in general" (ruling Q8).

B4 The three rules of thumb (spec v0.17 §7, check 5; ruled Q11). Each is an answer, scored like any other; no pass/fail. Each rule ranks the elements a model acts on: nodes for the offensive model; damaged elements (the jobs) for the restorative model; nodes and every element the storm can damage for the defensive model.
- **Most connections first:** rank by degree: within-layer links plus couplings, switched on and hidden. A line's degree is the number of elements it joins (2). Ties go to the lowest id.
- **Biggest first:** rank by the element's share of its own layer's total capacity, in that layer's unit. An element whose class carries no capacity ranks last; mark which classes those are as a `CHOICE:` and list them in the report.
- **Nearest supplier:** build a copy of the true world in which every consumer's coupling goes to its nearest eligible supplier of that commodity. The copy keeps the true scenarios' damage on every element it shares with the true world; a coupling that exists only in the copy takes no damage. So the failed elements, and the restorative jobs, are the same on both. Solve the request on the copy by the same search, then score that answer on the true world.
- **How a ranking becomes an answer:**
  - offensive: strike the top k;
  - restorative: crews take jobs in rank order, each crew taking the next unassigned job when it comes free;
  - defensive: among all affordable answers whose actions target only the top m ranked elements, where m is the budget (the most actions it could buy), take the best. A reserve may go on any dependency of a node in the top m, and protection on any element in it. Report the ranking and the answer.

B5 Every search, for every model, falls under one ceiling (ruled Q8):
- **time it first:** before a search starts, run a fixed sample, project the full time and print the projection;
- **the ceiling:** 48 hours per request on the build machine, covering its main search and its rules of thumb together. It is a registry rule, placeholder (open decision 6: the exact-tier instance bound). A main search whose projection exceeds it stops before starting and is reported with its answer count and projected time. A rule of thumb that would push the request past the ceiling is reported as not run, with its projection.

B6 The registry's objective entry "acceptability threshold" is retired, its text moved to the entry's history, citing decision 0018 (ruling Q11: no acceptability band in the key). The spec's Theta List no longer names it (v0.17).

PART C — THE RESTORATIVE MODEL (ruled Q2)

C1 A plan gives each crew an ordered list of jobs. Every failed element in the named scenario is repaired once, by one crew, and a crew may have no jobs. Both crews start at the base at hour 0. Travel, preparation and manual switching follow the engine's existing rules (spec §4.5).
- A manual switching job arises from the world's state, not from the plan. When one arises, the engine's existing rule takes it, as it does today. Say in the report whether any arises in scenario 7.

C2 The engine takes a plan as its crew policy, beside the default crew order. With the default order the engine is unchanged: all reference runs and the hand-trace test stay byte-identical.

C3 Search every plan: every split of the jobs between the crews, in every order. Report the count for scenario 7.

C4 Carry-over from PR 24: check `dynamics.floor_after_generator_stops` when a run starts, as the other two dynamics rules are checked, not only when a generator stops.

TESTS (10a):
- the schema migration, and its failure message;
- requests differing only in weights give the same search and the arithmetic-reweighted objectives;
- the plan policy equals the default order when the plan is the default order's own job sequence, step for step;
- on scenario 7, the default order's objective (52.25 weighted, Lifeline) appears among the plans' objectives, and the optimum is no worse;
- a tie in the optimum lists every tied plan;
- the zero range is reported, not divided;
- the key is byte-identical across two runs and on both platforms (golden: `tests/golden/pilot_answer_keys/`, restorative keys).

# PR 10b — The offensive model (ruled Q3, Q4)

D1 k nodes struck at hour 0 on the calm world, with no storm. A struck node takes complete damage (`repair` rules: complete crew work and parts lead time), and the crews repair it in the default order. Lines are not targets.

D2 Search every set of k distinct nodes: 276 at k = 2, 2,024 at k = 3. One run per set.

D3 The measure mirrors: an attack's distance is (optimum − its objective) ÷ (optimum − no-strike objective).

TESTS (10b):
- a struck node is out for the whole 72-hour window, and the crews' timelines show the repair job;
- k = 1 equals true criticality on the calm world, node for node;
- goldens for the four offensive keys.

# PR 10c — The defensive model (ruled Q5, Q6, Q7, Q8)

E1 Actions, up to the budget (a ceiling: units may be left unspent):
- **Protect condition** (cost 2): the element is undamaged in every scenario. Targets: every element the storm can damage: facilities, overhead lines and routed power feeds.
- **Add reserve** (cost 1): a stock on one inbound dependency of one node. Where the node has no stock for that dependency, a new stock is created; otherwise hours are added to the one it has. The reserve covers the request's window at the node's full draw. At most one reserve per (node, dependency).

E2 The engine creates the new stock (`AddReserve` today only adds hours to an existing one). A run with no actions is unchanged: reference runs and the hand-trace test stay byte-identical.

E3 The objective is the expected weighted service-hours lost over the 8 scenarios, equally weighted.

E4 Skip only what is provably identical, and say in the code why each holds:
- an answer that protects an element no scenario damages scores the same as the same answer without that protection;
- a scenario with no damage is run once with no actions, since no action changes it.

E5 Running it:
- spread the runs across every core and reuse what repeats;
- report the projections (B5) for both budgets before starting budget 4 (ruling Q8);
- the nearest-supplier rule of thumb (B4) is a second full search on its copy of the world. Under B5 it shares the request's 48 hours, so at budget 4 it may be reported as not run.

E6 CI cannot run budget 4. The defensive keys are checked in as goldens with their hashes. CI re-scores the optimum and a fixed sample of 100 stored answers, and checks the spread from the stored file. A full recomputation is a test marked `slow`, run locally before the PR; report its result and time.

TESTS (10c):
- a protected element is undamaged in every scenario; a reserve on a stockless dependency keeps the node up through a 72-hour cut of that supply, and a reserve on an existing stock adds to it;
- each skip in E4 holds: on a sample, the skipped answer, run in full, scores exactly what was assumed;
- spending under the budget is searched;
- goldens for the four defensive keys.

# PR 10d — The MIP cross-check (outline; ruled Q10)

F1 A time-expanded mixed-integer program of the same dynamics, at the same 15-minute steps, for the defensive, offensive and restorative models:
- trips as binaries;
- stocks;
- crew travel, preparation and work.
It is built from the true world's data, not from the engine's code, so that it is an independent check.

F2 Solved with HiGHS (`highspy`, MIT licence), single-threaded with a fixed seed.

F3 Agreement: the MIP's optimum objective equals brute force's to within an absolute tolerance, a registry rule, placeholder (open decision: MIP agreement tolerance), proposed at 1e-6 weighted service-hours: an allowance for floating point only. Where answers tie, any tied answer agrees. The key records agreement and the MIP's objective rounded to 6 decimals; nothing else from the MIP reaches the key.

F4 The default crew order as constraints is the hard part. The design side sends a short ruling sheet on it before this PR starts.
